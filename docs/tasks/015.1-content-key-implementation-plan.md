# Implementation Plan: Stable Content Keys for Prepared Chapters

## Purpose

Implement a deterministic `content_key` for every prepared chapter artifact.
The key identifies an exact normalized chapter text within one Gurubodh subject
and language. It is intended for artifact provenance, semantic chunking, and
future RAG retrieval; it is **not** a stable editorial chapter identity.

This plan intentionally closes only the low-complexity part of Task 015. It
does not introduce chapter revisions, a chapter-identity registry, CMS content
types, a vector database, or a retained-history workflow.

## Decisions Fixed by This Plan

### Identity model

Use two different concepts:

| Field | Meaning | Stability |
| --- | --- | --- |
| `content_key` | Deterministic identity for the normalized text of one chapter in one subject and language. | Stable across reruns and storage backends when the normalized text is unchanged. |
| `generated_chapter_number` | Position assigned by the chapter splitter. It remains the existing `document.chapter_number` field. | May change when a subject is re-split. It is not identity. |
| `integrity.artifacts.text` checksum | SHA-256 of exact bytes stored in the chapter `.txt` artifact, including its final LF. | Verifies the stored file; not used as `content_key` input. |

Do not add `chapter_key` or `chapter_revision_key` in this scope.

### Content-key formula

Define `content_key` as UUID v5:

```text
UUIDv5(GURUBODH_CONTENT_NAMESPACE,
       "v1|" + category_code + "|" + subject_code + "|" + language + "|" + normalized_content_sha256)
```

`GURUBODH_CONTENT_NAMESPACE` must be a single documented, immutable UUID
constant owned by Gurubodh. The string is UTF-8 encoded for the UUID v5 name
calculation. Delimiters and the literal `v1` are required to make the input
unambiguous and to permit a future incompatible identity contract to be
introduced explicitly rather than silently changing keys.

Including category, subject, and language means identical text in different
subjects or language variants has a different `content_key`. Identical text in
two generated chapter positions in the *same* subject/language has the same
`content_key`; this is deliberate content deduplication behavior. The output
metadata still preserves two separate generated chapter numbers and artifact
references.

### Normalized-content checksum contract

Add a separate `normalized_content_sha256` field. Its input is generated from
the chapter text before the `.txt` artifact's final newline is appended.

Normalization v1 must perform these steps in order:

1. Normalize Unicode to NFC.
2. Convert `CRLF` and lone `CR` line endings to `LF`.
3. Remove trailing spaces and tabs from each line.
4. Remove leading and trailing Unicode whitespace from the full text.
5. Preserve all internal whitespace, paragraph boundaries, punctuation, and
   characters exactly after the preceding steps.

The normalized checksum is SHA-256 of the UTF-8 encoding of the resulting
string. No final newline is added for this checksum.

This deliberately differs from the existing exact-artifact checksum and from
the semantic chunking code's whitespace-insensitive validation checksum. Do
not replace or reinterpret either existing checksum.

The normalized text itself does not need to be stored, because the canonical
chapter `.txt` artifact and the documented algorithm can reproduce it.

## Scope

### In scope

- A reusable content-normalization and content-key helper in the Gurubodh CLI.
- Chapter metadata schema and generated metadata fields for `content_identity`.
- Deterministic keys in both local and R2 `prep-subject` outputs.
- Propagating source `content_key` and normalized checksum into semantic chunk
  artifacts and chunk-generation audit records.
- Subject-output manifests that let downstream RAG work identify the currently
  generated set of chapter content without treating generated chapter numbers
  as identity.
- Tests, documentation, and migration behavior for existing artifact trees.

### Explicitly out of scope

- Logical chapter identity that survives a text edit.
- Revision numbers, revision history, restore, overwrite/create-revision
  policies, and import-job persistence.
- Changes to the existing `--overwrite` behavior beyond preserving correct
  content-key generation during an overwrite run.
- Strapi schema, CMS ingestion, database migrations, vector-store tables, and
  retrieval-service implementation.
- Automatic matching of two similar-but-not-identical chapter texts.

## Target Artifact Contract

### Chapter metadata

Add this required object to every newly generated chapter metadata JSON:

```json
{
  "content_identity": {
    "algorithm": "uuid5",
    "namespace": "<documented Gurubodh UUID>",
    "identity_contract_version": 1,
    "normalization": "gurubodh-chapter-content-v1",
    "normalized_content_sha256": "<64 lowercase hexadecimal characters>",
    "content_key": "<canonical lowercase UUID>"
  }
}
```

`document.chapter_number` remains unchanged and continues to describe the
generated display/order position. It must not be added to `content_identity`.

Keep `integrity.artifacts.text` unchanged. It is the checksum of the emitted
artifact bytes and remains useful for transport and file-integrity checking.

### Chapter content manifest

Write a generated manifest at:

```text
<subject>/chapters/chapter_content_manifest.json
```

For R2, the equivalent object is:

```text
<destination-prefix>/<subject-dir>/chapters/chapter_content_manifest.json
```

Initial contract:

```json
{
  "schema_version": 1,
  "identity_contract_version": 1,
  "subject": {
    "category_code": "CAT001",
    "subject_code": "SUB123",
    "language": "hi-Deva"
  },
  "chapters": [
    {
      "generated_chapter_number": "003",
      "content_key": "...",
      "normalized_content_sha256": "...",
      "metadata_artifact": { "backend": "local", "path": "...", "url": null },
      "text_artifact": { "backend": "local", "path": "...", "url": null }
    }
  ]
}
```

For R2, the artifact-reference shapes use the project’s existing bucket/key
convention. The manifest must be deterministically ordered by generated chapter
number and then metadata path.

The manifest describes the chapter set generated by this subject run. It does
not establish revision history or a permanent logical chapter registry.

### Semantic chunk artifacts

Update each `*.chunks.json` artifact to include a source content-identity
object copied from its source chapter metadata:

```json
{
  "source_references": {
    "content_identity": {
      "content_key": "...",
      "normalized_content_sha256": "...",
      "identity_contract_version": 1
    }
  }
}
```

Retain existing artifact byte checksums and whitespace-insensitive semantic
chunk validation fields. No embedding configuration or vector-storage change
is required in this task.

## Implementation Steps

### 1. Confirm the implementation issue and branch

Before modifying tracked files, create a dedicated implementation issue that
links to Task 015 and this plan. Work on a dedicated branch named using the
repository convention, for example:

```text
issue-<number>-chapter-content-key
```

Task 015’s Issue #176 may be closed after this plan is accepted; do not use a
closed design-discussion issue as the implementation issue.

### 2. Add the canonical identity helper

Create a small CLI-owned module, for example
`gurubodh/content_identity.py`, containing:

- the namespace UUID constant;
- `normalize_chapter_content_v1(text: str) -> str`;
- `normalized_content_sha256(text: str) -> str`;
- `content_key(category_code, subject_code, language, normalized_sha256) -> str`;
- `build_content_identity(...) -> dict` for metadata serialization.

Validation rules:

- Reject blank category code, subject code, language, and checksum values.
- Require checksums to be 64 lowercase hexadecimal characters before building
  the UUID name.
- Return canonical lowercase UUID strings.
- Keep the normalization implementation free of model or storage dependencies.

Add unit tests using Devanagari input for NFC normalization, mixed line endings,
trailing whitespace, leading/trailing whitespace, internal-space preservation,
and repeatability.

### 3. Generate content identity during chapter splitting

In the chapter metadata construction path:

1. Continue generating `chapter_text_value` as today.
2. Build `content_identity` from the configured category code, subject code,
   metadata language, and `chapter_text_value`.
3. Add `content_identity` to the generated metadata JSON.
4. Keep `integrity.artifacts.text` based on the exact bytes that will be
   emitted to the `.txt` artifact.

The content key must be generated before storage-specific references are added
or serialized so local and R2 runs produce the same key for the same content.

Do not derive it from filename, path, subject directory, generated chapter
number, title slug, timestamp, source object key, or destination backend.

### 4. Define and validate the schema

Update `chapter_metadata.schema.json` to require `content_identity` for all
newly generated metadata. Validate:

- `algorithm` is `uuid5`;
- `identity_contract_version` is integer `1`;
- `normalization` is `gurubodh-chapter-content-v1`;
- `normalized_content_sha256` matches `^[a-f0-9]{64}$`;
- `content_key` matches canonical UUID format;
- namespace matches the documented constant if the schema convention supports
  a constant value.

Update schema examples and the schema index. Preserve read compatibility for
old metadata during the migration period: readers should emit a clear error
that identifies the artifact and instructs operators to regenerate or run the
migration command described below.

### 5. Generate the chapter content manifest

After all chapter text and metadata files are successfully written, collect the
metadata into `chapters/chapter_content_manifest.json`.

Requirements:

- Include only artifacts created for the current subject output.
- Use existing storage-reference helpers to make local/R2 artifact references.
- Validate every manifest entry’s checksum and content key against its chapter
  metadata before writing the manifest.
- Write the manifest before the successful local audit report so it is included
  in local artifact counts and audit output.
- Include it in R2 publishing with all generated artifacts.

For R2, upload the manifest after its referenced chapter artifacts. The current
single-entry-point constraint makes this sufficient for the first release; the
plan does not claim multi-writer atomicity. A future concurrent-writer design
should publish a versioned manifest and atomically advance a current pointer.

### 6. Propagate identity into chunk generation

Update `generate-chunks` so it:

1. Requires valid `content_identity` in source chapter metadata.
2. Copies the relevant identity fields into every generated semantic chunk
   artifact.
3. Includes `content_key` in chapter summaries and machine-readable audit
   reports.
4. Fails before model work for any selected chapter whose identity is missing or
   invalid, with an action-oriented regeneration/migration message.

This binds chunks and embeddings to the exact normalized source content without
making a claim about logical chapter history.

### 7. Add explicit migration support for existing outputs

Existing prepared artifacts lack `content_identity`. Do not silently edit them
during an ordinary `generate-chunks` run.

Add one explicit, dry-run-capable CLI operation, for example:

```text
gurubodh add-content-identity --config <prep-subject-job> [--dry-run] [--overwrite]
```

It must:

- load existing chapter `.txt` and metadata pairs;
- verify the existing exact-artifact checksum before making changes;
- generate and validate `content_identity`;
- write updated metadata and `chapters/chapter_content_manifest.json`;
- support both local and R2 artifact trees;
- write the standard JSON/Markdown audit records;
- never alter chapter text, DOCX files, generated chapter numbers, or existing
  checksum fields.

Alternatively, if command-surface expansion is undesirable, require complete
`prep-subject --overwrite` regeneration as the only migration path. Choose one
approach in the implementation issue; do not implement both without need.

### 8. Documentation and operator behavior

Update the CLI README, prepared-content interface contract, and schema index to
state:

- what `content_key` represents and what it does not represent;
- the normalization-v1 rules;
- that generated chapter numbers are display/order fields;
- that reordering unchanged text preserves `content_key` but changes its
  generated chapter number and path;
- that a text edit changes `content_key` and requires fresh derived chunks;
- the migration/regeneration procedure for artifacts created before this work.

Update Task 015 only if the accepted decision is to narrow or supersede its
`chapter_key` proposal; otherwise create a new implementation task/issue that
links back to it.

## Required Tests

### Unit tests

- Same normalized text produces the same checksum and content key across
  repeated calls.
- NFC/NFD-equivalent Devanagari input produces the same identity.
- LF, CRLF, and CR variations produce the same identity.
- Trailing line spaces/tabs and outer whitespace produce the same identity.
- An internal whitespace or punctuation change produces a different identity.
- Changing category, subject, or language produces a different identity.
- UUID, namespace, checksum format, and blank input validation behave as
  specified.

### Prep-subject integration tests

- A local run writes valid `content_identity` into each chapter metadata file
  and a valid deterministic subject manifest.
- Equivalent local and fake-R2 runs produce identical content keys and
  normalized checksums.
- Reordering the same chapter text changes generated order/file paths but not
  its content key.
- Changing a chapter’s text changes only that chapter’s content key.
- Two identical chapter texts in one subject have the same content key and
  remain two manifest entries with distinct generated chapter numbers.
- Existing artifact byte checksums remain valid and unchanged in meaning.

### Chunk-generation integration tests

- Chunk outputs copy valid source content identity.
- Missing or invalid source content identity causes a clear pre-model failure.
- A changed source `content_key` changes the chunk-artifact provenance, even
  when the chunking configuration is unchanged.

### Migration tests, if the migration command is selected

- `--dry-run` changes nothing and reports proposed updates.
- Local and fake-R2 migrations preserve text and exact artifact checksums.
- A corrupt/mismatched artifact checksum fails without changing metadata.
- Re-running migration is idempotent.

Report each skipped verification explicitly, including the reason.

## Acceptance Criteria

- Every newly generated chapter metadata file includes a valid,
  deterministic `content_identity` object.
- The same chapter text and subject/language identity produce the same key for
  local and R2 outputs.
- Generated chapter number is not an input to the content key.
- A content edit produces a new content key; reordering unchanged content does
  not.
- A subject manifest lists the generated content keys and references for the
  current output set.
- Semantic chunk artifacts and audit records carry source content identity.
- Existing artifact-byte checksum behavior remains intact.
- No revision-history, stable logical chapter identity, CMS, database, or RAG
  retrieval behavior is implied or implemented.

## Future Compatibility

If Gurubodh later needs editorial identity across corrections, add a separate
logical chapter entity keyed by a verified source identifier or an operator
maintained registry. That entity may relate multiple `content_key` values over
time. This plan does not prevent that evolution: `content_key` remains the
provenance key for each exact content state.
